# ADR-0024: Single sign-on is OIDC, and only OIDC

## Status

Accepted and implemented.

## Context

Requested: Keycloak, and "the common auth systems" generally, configurable in
the administration area and by environment.

Keycloak, Authentik, Authelia, Zitadel, Google, Entra ID, Okta and GitLab all
speak OpenID Connect. Building "Keycloak support" would be building one of them
badly; building an OIDC client makes each of them a configuration rather than a
code path.

## Decisions

### One protocol

OIDC, discovered from the provider's `.well-known/openid-configuration`.
Authorization code flow with PKCE. Nothing provider-specific is written down —
if a provider needs a special case to work, that is a bug in how generally this
was built, not a reason for a second implementation.

**SAML is not implemented.** It is a second protocol with its own cryptography
and its own failure modes, and it would double the surface of the one part of
this application where a mistake is unrecoverable. Asked for and declined for
now; the people who need it can usually also speak OIDC.

### Secrets by environment, everything else in the interface

A client secret goes in `SONE_OIDC_CLIENT_SECRET` and nowhere near the database.
A secret in a table is a secret in every backup, and a secret in a form is one on
a screen. Everything else — issuer URL, client id, button label, whether sign-up
through the provider is allowed — is a workspace-independent instance setting,
edited in the administration area, because it is the sort of thing changed while
looking at the result.

The instance therefore refuses to enable OIDC when the secret is missing, rather
than starting in a half-configured state that fails at the moment somebody tries
to sign in.

### Accounts are matched on `sub`, never on email

The provider's `sub` claim is the identity. An email is a label: it can be
changed, reassigned, and at some providers claimed without proof. Matching on it
means whoever can change an address at the identity provider can take over the
account it names.

The email is used once, when an account is first created, and after that it is
just a display value. An existing local account is **not** silently adopted by a
matching email — linking one is a deliberate act by somebody already signed in.

`email_verified` is required for account creation. A provider that will not say
whether it verified an address has not verified it.

### Local passwords stay

Both ways in, side by side, as asked. That is a real decision and not only a
convenience: an instance whose only door is an identity provider is an instance
that cannot be repaired when that provider is unreachable, and self-hosted
software should not have a failure mode that requires somebody else's service to
be working.

The **instance administrator can always sign in with a password**. Whatever else
is configured, that path is never removed — a lockout of the only person who can
fix the configuration is the failure this must not have.

### Roles are not taken from groups

Tempting, and deferred deliberately. Mapping provider groups to workspace roles
makes the identity system the authority on who may do what here, and that is a
larger decision than signing in: it means a change made in a directory silently
changes permissions in documents. Sign-in first; if group mapping is wanted
later it can be added without changing anything decided above.

## Consequences

A new provider is a form to fill in, not a release.

The sign-in page grows a button when OIDC is configured, and keeps the password
form. Somebody with both can use either.

Tests run against a simulated provider — issuing real tokens signed by a key the
test controls, so discovery, PKCE, the state check, signature verification,
issuer and audience checks and clock skew are all exercised. Testing an auth
flow against a mock that always says yes tests nothing, and this is the one area
where that would be worth catching late.

> **Correction, 2026-09-05 (ADR-0082).** The paragraph above was true of the
> *pieces* and false of the whole, in the way that mattered most. Discovery,
> PKCE, signature verification, issuer, audience and skew were all genuinely
> exercised — seventeen negative cases against real RSA-signed tokens. The state
> check was exercised only as the bare `statesMatch` helper, never in the
> callback that calls it, and **nothing signed a real token and delivered it
> through a route**: `oidcRoutes.ts` was imported by `main.ts` and by nothing
> else. The file named `oidcRoutes.db.test.ts` asserted database constraints and
> did not import it.
>
> The first test that ran the callback found that signing in through a provider
> had never been able to create an account: `ON CONFLICT (email)` matches no
> index on `users`, so every first sign-in threw and became `401
> sign_in_failed`. The sentence above is why nobody looked — reading it, this
> feature was in good shape. That is the failure mode a record can have that
> code cannot.
>
> Also described here and not built: linking an existing account, "a deliberate
> act by somebody already signed in". There is no such route, so every
> pre-existing local user is unable to use SSO at all.

## Alternatives considered

**A provider-specific integration for Keycloak.** Rejected above: it is the same
work with a smaller result.

**Matching accounts by email.** Rejected: it makes account takeover a matter of
changing a string somewhere else.

**Replacing local passwords.** Rejected: it hands the ability to enter your own
instance to a service you may not control.
