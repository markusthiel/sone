# ADR-0020: Tags are names on the page, and the tag list is derived

- **Status:** Accepted
- **Date:** 2026-08-28
- **Relates to:** ADR-0002 (CRDTs are truth), ADR-0019 (folders), ADR-0011 (search)

## Context

Folders answer "where does this live". Tags answer "what is this about", and the
two are wanted for different reasons: a page lives in exactly one folder and can
carry any number of tags, and a tag crosses folders — a meeting note about a
project belongs in the meetings folder and should still be findable from the
project.

Three questions have to be answered together, because the wrong combination
produces something that cannot be rebuilt or cannot be renamed.

## Decision

### Where a tag lives

**On the page's document, as a list of names.** A tag is a property of the page:
everyone looking at it sees the same tags, so it belongs where the title and the
parent belong. That is the same reasoning as ADR-0019 for folders, and the
opposite of favourites — a favourite is one person's, so it is Postgres-only.

### What identifies a tag

**Its name, normalised.** Not an id.

An id would need a workspace-level registry of tags, and a registry is not part
of any document — so it could not be rebuilt from the CRDT log, and ADR-0002's
guarantee would be spent on tag names. It would also mean two people creating
"meeting" offline produce two different tags that look identical.

The cost is that renaming a tag is a bulk edit: every page carrying it has to be
rewritten. That is honest about what is actually happening, and it is a rare
operation. The alternative hides the same work behind an id and buys a registry
that cannot survive a rebuild.

Normalisation is case-insensitive and whitespace-collapsing, so `Meeting`,
`meeting ` and `  MEETING` are one tag. The **first spelling used** is kept for
display: a tag typed as `Meeting` shows as `Meeting`, and typing `meeting` on
another page joins it rather than creating a second.

### Where the list of tags comes from

**Derived from use.** A tag exists because a page carries it; there is no
separate place to create one. The projection maintains a `page_tags` table, and
"the tags in this workspace" is a query over it.

That means an unused tag disappears, which is the right behaviour: a tag nobody
has applied is not a tag, it is a typo somebody made once.

## Consequences

Everything about tags is rebuildable from the CRDT log, including the tag list,
because the list is a query rather than a record.

Tag colours and icons are **not** decided here and are not implemented. They
would need per-tag data that no document owns, which is the registry problem
again. If they are added, the honest form is a workspace-level table that is
explicitly decorative: losing it loses colours, never tags. That distinction has
to be written down before the table is, or the next person will assume it is
authoritative.

Renaming a tag across a workspace is not implemented either. It is a bulk
document edit and belongs with the other maintenance operations rather than in a
tag chip's context menu, where its cost would be invisible.

Search already indexes title and body (ADR-0011). Tags are indexed alongside, so
a tag name typed into search finds the pages carrying it without anyone learning
a filter syntax.

## Alternatives considered

**A tag registry with ids.** Rejected: not rebuildable from the CRDT log, and
offline creation of the same tag produces duplicates.

**Tags in Postgres only, like favourites.** Rejected: a tag is visible to
everyone who can see the page, so it is page data. Keeping it out of the document
would make it invisible to an export and unrecoverable from a rebuild.

**Hierarchical tags** (`project/acme`). Rejected for now: it is a second tree
beside folders, and having decided that folders are the way structure is
expressed, adding a competing hierarchy would leave two answers to "where does
this go". Nothing here prevents adding it later, since a `/` in a name is
already a legal tag.
